# Security Agent Research Strategy

## Purpose

Design a governed research-and-development program for a ResonantOS security agent that can:

- map every meaningful attack surface and attack vector in the app;
- generate a security architecture view of the current system;
- split red-team work into specialized, reusable skills;
- select existing tools before inventing local checks;
- measure security maturity, identify gaps, and create deterministic tests;
- feed validated checks into the existing registry-driven security pipeline.

This is a strategy artifact, not permission to run invasive tests. Any active exploitation, destructive probing, broad network scanning, credential attack, or persistence simulation must pass an explicit approval gate first.

## Starting Evidence

Existing starting points:

- The first `security-reviewer` run identifies real surfaces across Tauri IPC, webview/CSP, capability gates, provider HTTP requests, local subnet discovery, subprocess delegation, addon manifests, browser automation, Telegram, Paperclip, archive storage, local files, logs, and supply chain.
- The `threat-model-profiler` run adds entry-point and topology evidence for browser-first bridge routes, side-panel extension communication, Electron IPC mode, local listener bind behavior, bridge/capability tokens, memory-service host overrides, terminal shell execution, native library loading, hardcoded LAN endpoints, unsigned artifacts, and the missing `SECURITY.md` disclosure surface.
- The existing security pipeline MVP already defines a registry-driven check control plane in `.github/security-pipeline/checks.yml`.
- The MVP has completed `SWU-SP-001` through `SWU-SP-003`; `SWU-SP-004` is blocked in this shell by missing `npm`.

The new security agent should not replace that pipeline. It should sit above it as a research, design, red-team simulation, and maturity-scoring system that emits checks and evidence into the pipeline.

## Strategy Shape

Use a DAG, not a single linear audit.

The work has dependencies:

1. Asset and architecture mapping must happen before threat modeling.
2. Threat modeling must happen before selecting red-team simulations.
3. Safe static and unit-level tests can run before active dynamic tests.
4. Active tests require authorization and scoped fixtures.
5. Maturity scoring depends on evidence from mapping, tooling, test results, and remediation decisions.

The DAG approach has merit because each surface can be researched independently while still joining through a common evidence contract. It also prevents the agent from jumping directly from a finding to an exploit without architecture context, owner boundary, and approval.

- scope and explicit out-of-scope boundaries;
- input discovery commands;
- safe default tests;

For skill and agent validation, the evidence must also include:

- scripts and hooks invoked by the skill or agent;
- network-capable commands such as `curl`, `wget`, `fetch`, `Invoke-WebRequest`, `reqwest`, `axios`, `netcat`, and webhook clients;
- secret and user-data access patterns, including `.env`, SSH keys, cloud credentials, browser profiles, wallet paths, token files, and `.resonantos/`;

## Maturity Model

Score each surface at one of five levels:

| Level | Name | Meaning |
| --- | --- | --- |
| 0 | Unknown | Surface exists but is not mapped or tested. |
| 1 | Mapped | Assets, flows, boundaries, and obvious vectors are documented. |
| 2 | Guarded | Current controls are documented and at least one deterministic test exists. |
| 3 | Stress-tested | Safe red-team simulations or fuzz/property tests exercise likely abuse paths. |
| 4 | Managed | Checks are in CI or a repeatable local harness with evidence, owners, and remediation lifecycle. |

The initial target is level 2 for every surface, level 3 for the highest-risk surfaces, and level 4 for supply chain plus any fix that becomes a regression risk.

Installed agent skills have a stricter readiness rule: a skill cannot be used as a security-control primitive until it reaches level 2. That means it is installed, discoverable, structurally valid, has required support files, and its command or resolver path can be smoke-tested.

Agent skills and agents also require a hostile-content rule: a skill cannot reach level 2 if it contains unexplained network egress, shell execution, secret reads, memory mutation, persistence, or broad filesystem access that is not justified by its purpose and approved by the operator.

## Red-Team Test Policy

Default allowed without additional approval:

- static scans;
- unit tests and fixtures;
- offline malicious-content review of skills, agents, scripts, hooks, and command files;
- permission-to-purpose review for tool calls and runtime permissions;
- network/shell/secret-access inventory without executing those operations;
- local path traversal fixtures inside temporary directories;
- IPC payload tests against mocked or test-only commands;
- dependency and secret scans;
- architecture and threat-model research.

Requires explicit approval:

- active scanner runs such as ZAP activeScan or broad Nuclei templates;
- executing suspicious skill scripts or hooks;
- live network egress tests from installed skills or agents;
- local subnet probing beyond existing code inspection;
- exploit chains that write outside a temp directory;
- credential overwrite/delete simulations against real app state;
- browser/CDP takeover demonstrations against live user profiles;
- tests that call paid external provider APIs or Telegram/Paperclip endpoints.

Always blocked unless separately authorized in a dedicated task:

- persistence, malware-like behavior, exfiltration, destructive deletion, self-replication, or attacks against third-party systems.

## Promotion Path

Research outputs should flow into implementation through this sequence:

1. Create or update a skill design for one surface family.
2. When any finding requires development, do not implement directly from the research note. Create an invoke handoff route using the exact transition sentence: `$invoke handoff use context builder to prepare development for <finding-or-surface>`.
3. The handoff must use `context-builder` to gather the smallest sufficient repository evidence, target files, constraints, validation commands, and risk boundaries for that specific development item.
4. Generate safe tests and fixtures for that family only after the handoff defines the implementation boundary.
5. If useful, add a check adapter to `scripts/security-pipeline/checks/`.
6. Add a registry entry to `.github/security-pipeline/checks.yml` with `observe` or `warn` first.
7. Promote to `block` only after deterministic validation and low false-positive risk.
8. Record maturity score changes and remaining gaps.

Development trigger rule:

```text
$invoke handoff use context builder to prepare development for <finding-or-surface>
```

Use this whenever a mapped gap, failing maturity criterion, missing control, unsafe default, vulnerable dependency, malicious-skill signal, or red-team test idea becomes an implementation candidate.

### Boundary detail

#### B1: User / web content → Tauri webview (Tauri mode)

- **Transport:** In-process webview render
- **Validation:** Tauri's built-in IPC serialization; CSP is **`null`** (disabled)
- **What crosses:** User-generated content, AI responses, filesystem paths, command names
- **Notes:** CSP=null means any XSS in the React frontend or in AI-generated HTML/markdown rendered inline would have unrestricted access to Tauri IPC commands. No `script-src` restriction.

#### B2: Tauri webview → Rust IPC commands

- **Transport:** Tauri `invoke()` (in-process, serialized JSON)
- **Validation:** `assert_addon_capabilities` / `assert_living_archive_host_access` — checks addon installation + capability grants stored in `runtime-state.json`
- **What crosses:** Command names, structured JSON payloads
- **Notes:** The capability grants are stored in a JSON file written by the Tauri app itself. No cryptographic signing; an attacker who can write to the state file can grant themselves any capability.

#### B3: Chrome extension → Bridge server (browser-first mode)

- **Transport:** HTTP to `127.0.0.1:{dynamic}`
- **Validation:** `X-ResonantOS-Bridge-Token` (constant-time, `randomBytes(32)`); `Access-Control-Allow-Origin` locked to `chrome-extension://cdpdmmalhmokbfcfgogoepnjplaakgnl`
- **What crosses:** AI chat prompts, memory read/write, provider credentials (write gated by capability token), file browse paths
- **Notes:** CORS restricts cross-origin reads to the specific extension origin. The bridge token provides a second factor. Other processes on the host can access 127.0.0.1 directly (CORS is browser-enforced only).

#### B4: Rust backend → SQLite (archive service)

- **Transport:** In-process via `rusqlite` (bundled SQLite)
- **Validation:** All queries use `params![]` parameterized binding
- **What crosses:** Archive document data, metadata, search terms
- **Notes:** No string-concatenated SQL found. Connection opened per-call (`Connection::open(db_path)`).

#### B5: Rust backend → AI provider APIs (outbound)

- **Transport:** HTTPS via `reqwest` (rustls-tls)
- **Validation:** TLS cert chain (system roots); API key in `Authorization: Bearer` header
- **What crosses:** User chat messages, context, system prompts, model outputs
- **Notes:** User message content is sent to external AI providers. No PII scrubbing layer observed before sending.

#### B6: Bridge server → Hermes / OpenCode CLI (subprocess)

- **Transport:** `spawn(command, args, { env: { ...process.env, HERMES_HOME } })`
- **Validation:** None — full host environment forwarded; child process identity = host user
- **What crosses:** Full host environment including any ambient API keys; Hermes prompt content
- **Notes:** Hermes and OpenCode are external CLIs with their own capabilities (filesystem, shell, network). Trust boundary is the CLI's own sandboxing (none observed).

#### B7: Electron renderer → Electron main process

- **Transport:** Electron IPC (`ipcMain.handle("resonantos:invoke")`)
- **Validation:** `contextIsolation: true`, `nodeIntegration: false`; `sandbox: false` for main window and chat window
- **What crosses:** Same command surface as Tauri IPC
- **Notes:** `sandbox: false` for main and chat windows means renderer has access to Node.js APIs if `contextIsolation` were bypassed. With `contextIsolation: true` this is not directly exploitable without a renderer RCE; the combination is noted as a posture fact.

#### B8: CI → artifact storage

- **Transport:** GitHub Actions → GitHub artifact storage
- **Validation:** `GITHUB_TOKEN` (implicit)
- **What crosses:** Built binaries (macOS .dmg/.app, Windows .msi/.exe, Linux .AppImage/.deb/.rpm)
- **Notes:** No code signing or notarization observed in the workflow. Artifacts are not signed. Distribution of unsigned binaries may trigger OS Gatekeeper warnings.

ResonantOS vNext is a **single-user desktop application**. There are no user accounts, no login/signup flows, no sessions, and no multi-tenant data. The auth model is fundamentally different from a web app: the "user" is always the local OS user running the app.

---

### Authentication mechanisms in use

#### 1. Tauri IPC (no external auth)

- **Mechanism:** None required beyond OS-level access to the running desktop process.
- **Who can call:** Any JavaScript executing inside the Tauri webview.
- **Authorization gate:** Addon capability grants stored in `runtime-state.json`.
- **No user login required.** Whoever runs the Tauri binary is the operator.

#### 2. Bridge server bearer token (browser-first mode)

- **Mechanism:** Static bearer token per session; `X-ResonantOS-Bridge-Token` header
- **Library:** Custom (`bridge-server.mjs`); `randomBytes(32)`, `timingSafeEqual`
- **Where verified:** Every incoming request, before routing
- **Token lifecycle:** Generated at bridge server startup; written to `bridge-config.generated.js` (mode 0o600); valid for the lifetime of the bridge server process
- **Revocation:** Process termination (token is in-memory + file; restarting generates a new token)
- **Client storage:** JavaScript `globalThis.__RESONANTOS_BRIDGE_CONFIG__` in the Chrome extension context

#### 3. Capability tokens (bridge server — scoped actions)

- **Mechanism:** Per-capability static token; `X-ResonantOS-Bridge-Capability-Token` header
- **Scopes:** `provider-credential-write`, `provider-routing-write`, `memory-settings-write`, `memory-source-browse`, `memory-source-scan`, `memory-source-manage`, `memory-source-move`, `memory-source-review`, `memory-source-intake`, `memory-source-file-intake`, `addon-execution-settings-write`, `browser-download-action`, `diagnostics-report-export`
- **Lifecycle:** Generated at startup (or supplied via env vars); same lifetime as bridge token
- **Purpose:** Sub-token model; different clients (e.g. extension vs. Hermes) can have different permissions

#### 4. AI provider API keys

- **Mechanism:** `Authorization: Bearer <key>` to external AI APIs
- **Storage:** `~/ResonantOS_User/Secrets/provider-secrets.json` (plaintext JSON)
- **No rotation mechanism in app**
- **No password hashing** — these are raw API key strings, stored as-is

#### 5. Telegram bot token

- **Mechanism:** Telegram Bot API token; HTTP bearer to `api.telegram.org`
- **Storage:** Same JSON file (`provider-secrets.json`)

#### 6. Electron IPC (no external auth)

- **Mechanism:** None — Electron contextIsolation + preload script boundary
- **Same no-user-account model as Tauri**

---

### No user account system

- No signup/login endpoints
- No password hashing (`bcrypt`, `argon2`, `scrypt`)
- No session cookies
- No JWT issuance
- No RBAC / roles
- No 2FA / MFA
- No account recovery flow

All of the above are absent by design — the app is local-only, single-user.

---

### Authorization model

- **Tauri:** Addon capability grants checked per command. Grants stored in JSON (no signing).
- **Bridge:** Bridge token (all routes) + capability token (sensitive routes). Two-factor for writes.
- **No row-level access control** — not applicable (single user).
- **No admin/user role separation** — single identity.

---

### Public (unauthed) surface on bridge server

Within the bridge server, all routes require the bridge token. There are no truly public routes — even `GET /status` requires the bridge token. From the host OS (non-browser contexts), any process that can connect to `127.0.0.1:{bridgePort}` can brute-force the token (though at 32 random bytes this is computationally infeasible).

### Five-question supply-chain evaluation for notable deps

For each notable dependency, five questions are assessed:
1. **Breadth/maintenance** — Is the dep broadly used and actively maintained?
2. **Version currency** — Is the pinned version current or lagging behind security fixes?
3. **Privileged surface** — Does the dep touch network, filesystem, exec, or native code?
4. **User-input reachability** — Can attacker-controlled input reach the dep's unsafe surface?
5. **Blast radius** — If the dep is compromised (malicious update / CVE), what is the impact?

---

#### 1. `vitest` ^3.2.4 (devDependency)

| Question | Finding |
|----------|---------|
| Breadth/maintenance | Widely used, actively maintained by Vite team |
| Version currency | **Lagging** — GHSA-5xrq-8626-4rwp is fixed in 4.1.8; current pin `^3.2.4` is never satisfied by 4.x |
| Privileged surface | Yes — UI server reads and executes files on the local filesystem |
| User-input reachability | Only when `vitest --ui` is running; local attacker or browser-based CSRF can reach port |
| Blast radius (compromise) | Dev-only; would allow code execution on a developer's machine when running tests with UI; not in production binary |

**Assessment:** Medium risk. Not shipped in the Tauri binary. Upgrade to vitest 4.x required to resolve CVE; this is a breaking-change version bump that needs attention in CI configuration.

---

#### 2. `libloading` 0.8 (Rust runtime)

| Question | Finding |
|----------|---------|
| Breadth/maintenance | Small, focused crate; actively maintained by the Rust ecosystem |
| Version currency | 0.8.x is current stable |
| Privileged surface | **Critical** — loads `.so`/`.dylib`/`.dll` files via `unsafe { Library::new(&path) }` at runtime |
| User-input reachability | Library path is sourced from env var `RESONANTOS_NATIVE_BROWSER_BRIDGE` or a fixed candidate list. If a user/process can set `RESONANTOS_NATIVE_BROWSER_BRIDGE`, they can load an arbitrary shared library |
| Blast radius (compromise) | Full native code execution in the Tauri process context with all user privileges |

**Assessment:** High risk on the configuration path. `RESONANTOS_NATIVE_BROWSER_BRIDGE` env var → arbitrary library load is a code-execution primitive. Env var is explicitly cleared after load (`std::env::remove_var`) suggesting awareness, but the window between process start and load remains exploitable. Candidate list fallback is bounded to known paths — safer than the env var path.

#### 3. `portable-pty` 0.8 (Rust runtime)

| Question | Finding |
|----------|---------|
| Breadth/maintenance | Wez Furlong's crate; widely used in terminal emulator projects; actively maintained |
| Version currency | 0.8.x is current |
| Privileged surface | **High** — allocates a PTY and spawns a shell process; paired with `sh -lc <user_command>` in `terminal_service.rs` |
| User-input reachability | Any JavaScript code running in the Tauri WebView can call `terminal_run_command` (one of the 128 registered IPC commands) and pass arbitrary shell commands |
| Blast radius (compromise) | Full shell execution on the host OS; `portable-pty` itself is not the risk — the risk is the pairing with unrestricted shell execution |

**Assessment:** The dep is sound; the usage pattern is the risk. `portable-pty` is being used correctly as a PTY layer. The threat is that `terminal_run_command` passes unsanitized input to `sh -lc` — any XSS or compromised extension reaching the Tauri IPC layer achieves OS code execution.

#### 4. `react-markdown` + `remark-gfm` (npm runtime)

| Question | Finding |
|----------|---------|
| Breadth/maintenance | `react-markdown` is widely used; `remark-gfm` from the unified/remark ecosystem; both actively maintained |

Verify `MessageContent.tsx` does not add `rehype-raw` or `allowDangerousHtml`. Current usage appears safe — no raw HTML plugins observed.

#### 5. `reqwest` 0.12 / `tungstenite` 0.24 (Rust runtime)

| Question | Finding |
|----------|---------|
| Breadth/maintenance | Both widely used, actively maintained Rust crates |
